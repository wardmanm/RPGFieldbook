# Ammo Undo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** End combat's **Undo recovery** takes the recovered ammunition back off the sheet and
leaves the fired ammunition spent, so the next fight starts from nothing fired (#170).

**Architecture:** `undoRecovery()` (`src/js/62-ammo.js`) reverses a recovery in two halves: the
stock (take back what was added or rebuilt, point repointed weapons back) and the record (put every
cleared `ammoSpent` entry back). End combat's Undo runs both, so the record half re-arms every shot
the fight already settled. Split the stock half out into a shared helper, keep `undoRecovery()`
exactly as it is, and give End combat its own `undoEndCombatRecovery()`: the stock half, then
nothing back on record. `undoRecoveryTap()`, End combat's Undo, calls the new one.

**Tech Stack:** plain browser JS (concatenated fragments, no modules), the Node test harness
(`src/tests/harness.js`, `src/tests/sheet.js`).

**Spec:** issue #170, and the design Mike approved in chat on 2026-11-06 (no spec file; copied
here):

- Undo recovery means the table says those arrows are gone (Mike's call).
- Undo takes the recovered arrows back off the stack, as it does now, and leaves the fired arrows
  spent. Nothing goes back on record. The next fight starts from nothing fired, and the weapon
  row's Recover button has nothing to pick up. If the DM says "you find 3", the player adds them by
  hand.
- The fight's line in the inventory log is corrected, as Undo already does, to read that nothing
  came back.
- Only End combat's Undo changes. A weapon row's Recover mid-fight keeps today's behaviour.
- Tests include the issue's exact case: fire 4, End combat, Undo, then a second fight with nothing
  fired reports nothing and adds nothing.

**Branch:** `issue/170-ammo-undo` in `.claude/worktrees/170`. Commit `src/` and this plan only,
never `dist/fieldbook.html` or `docs/CHANGELOG.md`.

## Root cause (confirmed before planning)

A throwaway run of the real source (fire 4 of 20 arrows, End combat, the window's Undo, a second
fight with nothing fired) printed, after Undo, `ammoSpent.s1 = {n:4, …}` and the stack at 16; the
second End combat then logged "Arrows: 4 fired, 2 recovered" and took the stack to 18. The entry
comes back in `undoRecovery()`'s last loop, over `rec.cleared` (`62-ammo.js`, "Object.keys(rec.cleared)
…"), which End combat's Undo reaches through `applyAmmoRecovery({quiet})` → `undoRecoveryTap()` →
`undoRecovery()`.

**Fact the brief assumed otherwise:** a weapon row's **Recover** (`recoverWeaponAmmo()`) toasts with
no Undo, and never has (`git log -S`). End combat's Undo is the only caller of `undoRecovery()` in
the app. "Keeps today's behaviour" for the row therefore means `recoverWeaponAmmo()` is not touched;
`undoRecovery()` keeps its record-restoring behaviour unchanged (the reversal a mid-fight recovery's
Undo would need), still tested, with no app caller after this change. Reported, not built.

## Global Constraints

- New checks go in their own block at the end of `src/tests/sheet.js`, **just before** the final
  `t118EndToEnd().then(…)` line: a synchronous block after that line runs while `t118EndToEnd()`
  has `openModal`, `toast` and `X.character` patched.
- No new character field; `ammoSpent` keeps its shape, so a save→load round trip is unaffected.
- The log line's correction is today's: `meta.back` less what End combat gave back, title rebuilt by
  `ammoLogTitle()` ("Arrows: 4 fired, 0 recovered").
- The End of combat window's words are unchanged ("Recovery undone").
- `./src/tests/run.sh` green at the end; build with `./build.sh --no-zip` before it (`rules-data.js`
  byte-pins `src/html` against the built file).

## Review Focus

- **A row's Recover mid-fight, then End combat, then its Undo:** the row's own recovery stays; only
  End combat's part comes off the line ("Arrows: 10 fired, 5 recovered" → "…3 recovered").
- **A stack End combat rebuilt from its copy** (every arrow fired): Undo removes it and leaves no
  entry, so the next fight cannot rebuild it.
- **A thrown weapon** (Dagger thrown to ×0, back to ×2): Undo leaves it on the sheet at ×0 with no
  entry, Throw disabled, no Recover.
- **Entries that gave nothing back** (the lone needle under Half): cleared by End combat, still
  cleared after Undo.
- **A shot fired since from what End combat gave back** (unreachable while the window is open, which
  makes the page inert, but the function must not count an arrow Undo took away): the shortfall comes
  off the entry fired since; a shot from arrows that were really there stays on record.

### Task 1: End combat's Undo leaves the fired ammunition spent

**Files:**
- Modify: `src/js/62-ammo.js` (`undoRecovery()` and its comment, `undoRecoveryTap()`,
  `applyAmmoRecovery()`'s comment; add `recoveryUndoable()`, `undoRecoveryStock()`,

- Modify: `src/js/87-combat-end.js` (`endFightUndoAmmo()`'s comment only)
- Test: `src/tests/sheet.js` (a new block at the end; three existing checks that assert the bug)

**Interfaces:**
- Produces: `recoveryUndoable(c, rec) → boolean` — the record-shape guard `undoRecovery()` opens with
  today (`c` set; `rec` an object, not `undone`, with arrays `added`, `made`, `repointed` and an
  object `cleared`).
- Produces: `undoRecoveryStock(c, rec) → {short, at}` — `undoRecovery()`'s `take()` over `rec.made`
  (rebuilt) then `rec.added`, then the repoint loop, moved verbatim. `short` is today's object keyed
  by `from` (entry id); `at` is a `Map` keyed by the item id `take()` was asked to take from, summing
  each shortfall.
- Produces: `undoRecovery(c, rec) → boolean` — unchanged behaviour: guard, inventory default,
  `livePre`, `undoRecoveryStock()`, then the existing restore loop over `rec.cleared` reading `short`.
- Produces: `undoEndCombatRecovery(c, rec) → boolean` — guard, `undoRecoveryStock()`, then for each
  `at` id with a shortfall and an entry of its own (own property of `ammoSpent`): `n` less the
  shortfall; at 0 the entry is deleted; otherwise `hits = min(hits, n)`,
  `misses = min(max(0, n − hits), misses)`, the rest of the entry kept. Never reads `rec.cleared`.
  Sets `rec.undone`. Once only.
- `undoRecoveryTap(rec, who, amend, opts)`: same signature, calls `undoEndCombatRecovery()`.
